Delivery Factory · Developer guide

How the delivery core runs.

For a developer about to change agentic-core, write a pack, or debug a run. It shows what runs, in what order, which file does each step, and where a change belongs.

Read first

The idea behind it, for an architect, is on the Delivery core concept page. This page assumes it: the fifteen stages, the four roles, the five-line result and the three endings are not explained again here.

Figure 1 · the parts

The parts, mapped to files

The same picture as The parts on the concept page, same boxes, same numbered connections. There each box says what it is responsible for; here it says which skill, path or script carries it.

The orchestrator is one skill, agentic-core:run-route, called the route driver below. It is the only part allowed to start a stage. Everything that decides is a script; a model is involved only where a skill runs.

  1. Host → driver. A person types /agentic-core:run-route <item> [autonomous], or CI runs shared/runner/route-agent.mjs with the same command. The skill sets disable-model-invocation: true, so a model never starts a run on its own.
  2. Driver → core scripts. Every check and every decision: pre-flight, run state, which stages run, is the envelope valid, what happens next. Each script prints one line and exits with a code the driver branches on.
  3. Driver → stage adapter. Skill(<pack>:<skill>), one stage at a time. The adapter declares context: fork, so it runs as an isolated subagent and its context dies with it.
  4. Adapter → provider packs. By role, never by product: the adapter calls the role operation's skill (shared/role-operations.md). Project config binds each role to one pack.
  5. Adapter → disk. It reads fact-record.yaml and, when re-invoked, its own answer. It ends by writing its envelope with emit-envelope.sh. Its chat message is ignored.
  6. Scripts → disk. capture-envelope.sh and run-stage.sh judge the envelope file; write-run-state.sh, write-progress-row.sh and write-orchestration-flag.sh record the stage.
  7. Driver → scm provider, once. Right after readiness, the last stage that writes nothing, the driver puts the run on its own branch. It is the only provider call the driver makes itself, apart from tracker.post_note when an autonomous run ends blocked.

Two hosts, one driver

Interactive or headless

An interactive run proves the orchestration; only a headless run proves the guardrails.

Interactive. A person types the command in Claude Code. A question is asked with AskUserQuestion.

Headless. The consuming project's CI workflow checks out the plugins at the pinned tag and runs node shared/runner/route-agent.mjs "/agentic-core:run-route <item>". The runner adds guardrails, not orchestration:

  1. It refuses to start without ROUTE_PLUGIN_DIR, with a policy that check-route-policy.sh rejects, or when the network allowlist cannot be locked.
  2. It write-protects the plugin directory, the committed settings and the policy file.
  3. It runs one Agent SDK session with permissionMode: "dontAsk": a call ROUTE_ALLOWED_TOOLS does not cover is denied.
  4. It enforces the policy's forbidden rules as disallowedTools and again in a PreToolUse hook that covers subagents. A Stop hook keeps the session alive until the driver records an ending.
  5. It caps turns, wall-clock time and budget from the policy; environment variables can only lower the caps.

The determinism boundary

Three layers, in numbers

The concept page names the layers. Here is what each one holds, and the two mistakes no run output would show.

Layer 1 · scripts

101 scripts in shared/lib/; 99 have a .test.sh beside them. No model, no tokens: CI can prove this layer.

Layer 2 · contracts

33 Markdown files in shared/. Each shape is defined once; everything else points at it with one line, because a restated rule drifts.

Layer 3 · the driver

One skill. It owns control flow and nothing else. A PreToolUse hook on Read (skills/run-route/scripts/check-driver-read.sh) denies it any file a stage wrote while a run is live.

The stage runner stops short of running the stage on purpose, and says so about itself:

It does not spawn the adapter itself — that is the one step above this script that genuinely needs a model, left to whichever skill drives a full route.— shared/lib/run-stage.sh

Isolation belongs to the adapter

An adapter that forgets context: fork still runs and still returns a valid envelope. Nothing visible fails; its context just piles up in the driver instead of dying with the stage. That is why validate-pack-manifest.sh checks the field: no run output would ever show the mistake.

Two result blocks

A stage ends with ## Result (verdict: pass | warn | fail | question, plus error_class on fail or question). A stage that fans out to subagents of its own gets ## Outcome (status: success | warning | failure) back from them. The two share no word, so a block from the wrong level fails validation instead of matching a branch by accident.

Gates

Ordinary stages with a fixed order

readiness, plan-gate and publish-gate are ordinary stages to the driver.

What makes them gates is the order inside, fixed by shared/gate-contract.md: deterministic criteria scripts first, then a reviewing model on what survives, on a stronger model tier.

In agentic-eds both reviewing gates run as the agent agentic-eds:eds-gate-reviewer (model: opus, effort: high, isolation: worktree, tools Read, Glob, Grep, Bash, Write). It reviews and never fixes, and writes exactly two files: <gate>-report.md and its envelope.

The worktree holds tracked files only, so the gate cannot find .ai/run-context/ by itself. The driver passes its own directory as the gate's one argument, project_root:. The harness may also run the gate without a worktree and say nothing; the gate checks that with agentic-eds/shared/scripts/check-gate-isolation.sh and writes isolation: present or absent in its report. Being unisolated never changes the verdict. The driver's snapshot and comparison are what hold the two-file rule either way.

Rejected alternatives

Proposals that do not come back

Kept so the same proposal does not return under a new name.

Wrong layer

A shell loop as the orchestrator

A script calling run-stage.sh in a loop. But run-stage.sh does not start the stage, on purpose. The loop would judge envelope files nobody wrote and pass having done nothing. Starting a subagent needs a skill.

Conflicts with pre-flight

A liveness probe instead of a declaration

Proving a capability by calling it gives false negatives on sandbox or network conditions the pack author does not control, and aborts a run before a branch exists. Pre-flight reads what each pack declares instead; a provider lists its preconditions with a probe and a remedy, and the read-only health skill runs them on demand.

Duplicate state

A second state file and a second progress file

run-state.json and progress.md already exist, with the two-hour resume window. Two files for one state diverge.

Category error

Priority, estimates and dependencies per stage

Order is already the stage list. That advice is for an agent tracking work across many sessions; a pipeline whose list is resolved up front does not have that problem.
