Delivery Factory · Part 6 · Prototype and Verify Design

A draft, measured against the design

Two steps of the EDS pack build and check a draft before the plan exists. eds-prototype writes the draft. eds-verify-design renders it in the browser role, compares it with the design reference, and edits the block's CSS within a fixed budget. This page follows both. Repo: agentic-eds

Checked in SKILL.md + scripts

Read in the two SKILL.md files, pack.yaml and the scripts they call, in agenticDraft/plugins, folder plugins/agentic-eds/, tag v0.2.12 and later. Paths are relative to that folder.

Prototype

A draft that goes through the real pipeline

The step runs only when the fact record shows a design source or a design mentioned in the item. Its inputs are four fixed files from earlier stages.

  • The draft is project content, not a standalone page

    It writes drafts/<item_id>.plain.html plus the target block's <name>.css and a minimal <name>.js. The SKILL.md states why: a separate throwaway structure would verify one DOM shape while shipping another. An older draft for the same item is overwritten.

  • A script picks the target block

    resolve-target.py takes the answer to its own earlier question if there is one, otherwise the distinct blocks/<name>/ paths named in the item. Exactly one candidate decides. Zero or several: the step returns a question with the candidates as options.

  • A block missing locally is copied from the pinned upstream collection

    copy-upstream-blocks.sh decides which names to copy. Each copied file keeps a one-line Apache-2.0 change notice. If the collection's manifest cannot be read, the block is built new and the report says it could not be checked.

  • It runs no linter and renders nothing

    Lint belongs to the lint stage, inside its own edit budget. The prototype report carries no lint line.

Where a value comes from

The design owns the number

Every value in the CSS has a line in the report: selector, property, value, source, token.

  1. variables: a design variable holding that value, under its own name.
  2. metadata: the node's width, height and position.
  3. design_context: a row of design-context-values.tsv, which design-context-values.py reads from the reference code: padding, gap, radius, spacing, typography. Each row is keyed by the element's node id.
  4. A project token is written only where an existing custom property holds the same value. A close token is recorded as the nearest one and never written in its place.
  5. A fixed width or height goes on an element only as a design_context row of that element's own node. check-size-origin.py fails the step on any fixed size this run added that no node ties to. Text that outgrows a fixed box overflows it while the box itself looks right, so a size the design does not put on the node is refused.

Viewport variants. When the reference holds several widths, viewport-overrides.py diffs them into a mobile-first base and one override block per breakpoint the project's stylesheet already has. A variant that falls in an interval another variant holds is not implemented. Its proposed threshold is recorded and not used.

Assets. An SVG goes to icons/, a raster image next to the draft. A name held by different bytes is split by content hash. If even that collides, the step asks a human to rename or remove the file. Nothing is overwritten.

## Design values
.t th:first-child — border-radius — 20px 20px 0 0
  — source: design_context — token: none
  — node: 1:196
.t tr:last-child td:first-child — border-radius
  — 0 0 20px 20px — source: design_context
  — token: none — node: 1:196

The report's own example: one node's corner radius, split across two selectors. Every component of a split is 0 or the node's own value.

Verify design

Measure, compare, edit, measure again

The step has no browser of its own. It calls the browser role's render, capture and measure, one invocation per call.

  1. Start the draft server. start-draft-server.sh reuses one that already answers. eds-serve's own server never mounts drafts/, which is why this step has its own. It never stops it afterwards.
  2. Render /drafts/<item_id>. A fail, a question or an invalid result block ends the step.
  3. pair-viewports.py lists the widths: each width the design was drawn at, plus 375, 768 and 1440, plus one more for any breakpoint interval none of those falls in. Each width is captured and measured on its own.
  4. Compare. compare-design-values.py checks the measured values against the design values: match, mismatch, unmeasured or approx. The screenshots are compared by the model by inspection, not by a pixel-diff library.
  5. Regression check at every width: check-breakpoint-regressions.py flags a word broken across lines, or a box narrower than its own min-width.
  6. Write the mismatch list, one tagged line each: [fixable], [content-asset gap] or [content-dependent]. count-fixable.sh counts the fixable ones. The count is the script's, not the model's reading of the list.
  7. Fixable left: check-fix-budget.sh says whether another edit is allowed. The pack declares fix_attempts: 2 for this stage, so up to two edits and three checks. The step also stops if the last edit left the list identical or longer.
  8. Edit only the block's CSS, and its JS only if a mismatch implies behaviour. Group mismatches by cause and change each cause once. Never answer a size mismatch with a new fixed size on text.

The loop runs inside the stage, in its own forked subagent. The route driver never retries a stage and never sees an edit: it reads one result block at the end. See How it runs.

Content is listed, not graded. A value that follows the design's content, such as the height of a text box, comes back as approx. It is never a match, never a mismatch and never answered by an edit. The report lists each one under ## Content-dependent, not graded.

Fonts. A design font the project does not declare is missing content. A mismatch whose only difference is where text sits is tagged a content-asset gap and not fixed. If the project has declared fonts out of scope, that geometry is set aside and named in the report.

# count-fixable.sh, output format (exit 1 / exit 0)
fixable: fixable=<n> gaps=<g> approx=<a>
nothing-fixable: fixable=0 gaps=<g> approx=<a>

The format is from the script's own header. Exit 1 means an edit is due. Exit 0 ends the loop before the budget is touched.

Pass and stop

Four verdicts, each from a script

Both steps end in the same result block the rest of the route reads.

  • Prototype · pass

    The block, the draft and the report are written, the size-origin check is clean, and no degradation applies.

  • Prototype · warn

    The target block already existed, so this run changed code that pages use today, ahead of plan approval. Also: the upstream collection could not be checked, an image-only design with no values, no design-system manifest to grade against, no exemplar block, a viewport variant not written, or an unoptimised raster image that will be committed.

  • Prototype · question

    More than one candidate block, or no block named at all. Or an icon name held by different bytes. The driver asks a person and re-invokes the stage once with the answer. In an autonomous run it ends the run blocked instead.

  • Prototype · fail

    A required input file is missing, a script refuses its input, or the size-origin check finds a fixed size no node carries.

  • Verify · pass

    The final check found no mismatch, and nothing else applies.

  • Verify · warn

    Every remaining entry is a content gap or content-dependent. Or: some value was only judged visually, a comparison ran at reduced resolution, the reference had no values, or the run edited an existing block.

  • Verify · blocked

    The draft server never answered. The stage returns a question with error_class: TRANSIENT, so the driver asks nobody mid-run: it ends the run blocked, with what a person does before starting again. A fix made inside the run would change files no plan step named, and publish-gate would refuse the change.

  • Verify · fail

    A fixable mismatch survives the budget or an edit that changed nothing. Also a missing input, an unresolved browser role, a missing draft file, a render failure, or another checkout's server holding the port.

What it doesn't cover

The limits, as stated

From the two SKILL.md files.

  • Ahead of the plan

    The prototype can change a real, in-use block before plan and plan-gate. A run that stops before implement can leave that change behind. The step makes it visible in the report every time and does not prevent it.

  • By eye

    The screenshot comparison is judgment, not a pixel diff. A reduced-resolution reference is recorded as such, so fine detail is never claimed as a pixel match.

  • Measured set

    Only the browser role's fixed property list is compared against the design. Margin, width and composite values are judged visually.

  • Implement

    The SKILL.md records that eds-implement did not yet know the draft files exist (gap G61). Whether it builds on the draft or overwrites it is left to that stage and to plan.
