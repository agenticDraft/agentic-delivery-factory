A plan, reviewed before it is built

Two steps of the EDS pack sit between the draft and the real change. eds-plan turns the ticket into requirements and steps. eds-plan-gate checks that plan with a script first and a separate reviewer second, and the route proves afterwards that the gate changed nothing. Plan

Requirements first, steps second

The step always runs. It needs no tracker, scm, design or browser role: everything it reads was written by earlier stages.

  1. Read three fixed files: the fact record and the sanitized spec from intake, and design-conventions.md from conventions. Any of them missing or empty ends the step with fail: a missing artifact is a broken route, not a case to work around.
  2. Copy a missing upstream block. copy-upstream-blocks.sh copies a block the item names that the pinned upstream collection holds and the project lacks. On a design route the prototype usually did this already, and it prints copied=(none). The plan's steps are then changes on top of those files.
  3. Derive requirements. The spec's requirement and acceptance-criteria text is split into atomic, testable statements, req-1, req-2, … in the order they appear. Two that say the same thing in other words are one. None at all: the step returns a question. It does not guess what "done" means.
  4. Apply the conventions artifact. Its ## Exemplars paths go into the plan's header for implement to open. The step does not survey the project itself: a gap in the artifact is a conventions bug to report, not one to paper over.
  5. Draft the plan: one step per unit of concrete work, each naming the requirement ids it satisfies, with its dependency and its verification in comment lines.
  6. Validate the shape. check-plan-criteria.sh answers two questions with no model involved: does every requirement map to a step, and does every step trace back to a requirement.
  7. Revise if it says no. check-fix-budget.sh reads the stage's fix_attempts from the pack, which is 1 for plan: one revision, two checks. The revision fixes exactly the reason the script printed. Out of budget: fail, with the script's reason verbatim.

The plan step does no research. The conventions step already surveyed the project, and re-deriving it here would let two answers drift apart.

The plan file

What the script reads, what the reviewer reads

One file, two readers. The script reads only requirements: and stages:. The comment lines are for the reviewer.

# Implementation plan for <item_id>
# Conventions: <exemplar paths, one-line note>

requirements:
  - req-1
  # req-1: <one-line restatement>
  - req-2
stages:
  - id: <step-id>
    satisfies: [req-1]
    # depends_on: none
    # verification: <how it is confirmed>
  - id: <step-id>
    satisfies: [req-2]
    # depends_on: <step-id>
    # verification: <how it is confirmed>

The shape is the contract. plan-criteria.md fixes only the two fields the script consumes: the closed list of requirements, and each step's satisfies list. Everything else a plan carries is for the reviewer.

What the script rejects. A requirement no step satisfies. A step whose satisfies list is empty, or names only requirement ids that do not exist. Two requirements with the same id. It exits 0 with valid: plan (<n> requirements, <m> stages), or 1 with invalid: and the exact requirement or step.

Plan steps are not route stages. A step is the unit of work between plan and implement, and its id must not reuse one of the fifteen stage ids.

Plan gate

A script first, a reviewer second

The stage runs as eds-gate-reviewer: model opus, effort high, in a worktree of its own. It reviews and never fixes.

  1. Check isolation. check-gate-isolation.sh compares the stage's working directory with the project_root the route handed it and prints isolation: present or absent. That line goes into the report as information. It never changes the verdict.
  2. Locate the run context. A worktree holds tracked files only, so the plan is not in it. The route passes the project root as an argument, and the gate first proves the plan belongs to this run: the fact record's item id must equal the plan's.
  3. Run the same shape script as plan. Exit 1 is criterion 1 or 2 answered no. Exit 2 means the script could not decide, and that is a fail too: "did not run" is never read as "passed".
  4. Run the design relevance check. check-design-relevance.sh compares the item's keywords with the element names in the design. No shared name: one finding, at most warn. No design reference: not run, no finding.
  5. Criterion 3, does the dependency order hold? No when a step depends on a later step or one not in the plan, when two steps depend on each other, or when a step says depends_on: none but edits a unit that does not exist yet and no earlier step creates.
  6. Criterion 4, is the verification defined? No when a requirement has no step with a verification note, when the note restates the requirement ("works as specified" can never fail), or when it names a command or path this checkout does not have.
  7. Drop every finding below the bar. A finding stays only if it names the exact requirement, step or path, and what goes wrong if the plan is built as written. The rest is dropped, not softened with "possibly".

A criterion has two answers and no third. "Mostly holds" is the answer of a gate that cannot fail.

The guard

The route proves the gate changed nothing

The worktree should keep the reviewer away from the code under review. The harness does not always honour that, and nothing says when it doesn't.

Snapshot before. Before it invokes a gate, the route runs check-tree-unchanged.sh snapshot. It records HEAD and every path git status reports, with a hash of each file's content. A file already changed before the gate, the change under review, is part of the snapshot.

Compare after. When the gate returns, the route compares, allowing exactly two paths: the gate's report and its result block. Anything else changed, and the run ends failed on that stage, whatever its verdict said. The route does not even read the verdict.

A gate that ran without isolation but changed nothing passes the guard. Running unisolated never lowers a verdict on its own. See How it runs.

# plan-gate-report.md, its shape
# plan-gate report — <item id>

verdict: <verdict>
isolation: present | absent
relevance: match | low | not run (…)

## Criteria
1. yes | no | not reached — <what settles it>
2. …
3. …
4. …

## Findings
- <req, step or path> — <what goes wrong>

Pass and stop

Each verdict, and who decides it

Both steps end in the same result block the route reads. The route never retries a stage.

  • Plan · pass

    The shape script exits 0, on the first check or after the one revision. The result names the item and how many requirements the plan covers, nothing more. The detail is in plan.yaml.

  • Plan · question

    The spec carries no requirement or acceptance criterion to plan from. The driver asks a person and re-invokes the stage once with the answer. In an autonomous run it ends the run blocked instead.

  • Plan · fail

    A required file is missing, the upstream copy script refuses, or the shape script still says no after the revision.

  • Gate · pass

    All four criteria answered yes, and the report's findings say None.

  • Gate · warn

    All four answered yes, but at least one finding cleared the bar. A low design relevance score is one example. The run continues and the finding is recorded.

  • Gate · fail

    Criterion 3 or 4 answered no; or the shape script exits 1 or 2; or the relevance check cannot run; or the plan is missing or belongs to another run. The plan gate never asks a question.

  • Route · failed

    The gate changed any file other than its report and result block. The route names every changed path.

What it doesn't cover

The limits, as stated

From the two SKILL.md files and the criteria contract.

  • Best plan

    The gate does not judge whether this is the best way to build the change. Its four questions are coverage, no extra work, order, and checkable verification.

  • Two by judgment

    Criteria 3 and 4 are answered by a model. The bar it must clear is stated, and dropped impressions never reach the report, but the answer is still judgment, not a script.

  • Relevance

    Design relevance compares names, not pictures. It can only raise a warning, never fail a plan, and it never reads the design's text content.

  • Ignored files

    The tree guard sees what git status sees. Files ignored by version control are outside the snapshot.
